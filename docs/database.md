# Database

Beyond Borders runs on PostgreSQL 16 in development and production. SQLite
is only used for unit tests; the application itself targets Postgres
exclusively.

## Tables (Phase 1 + Phase 2)

| Table             | Purpose                                                                 |
|-------------------|-------------------------------------------------------------------------|
| `users`           | Auth identity, profile, password hash, currencies.                     |
| `sessions`        | Server-side session store (opaque ids, hashed cookies).                |
| `data_sources`    | Per-user registry of references that justify a cost or rate.           |
| `exchange_rates`  | User-entered FX rates, unique per (user, base, quote).                 |
| `study_plans`     | A user's scenario (destination, dates, base currency).                 |
| `cost_items`      | A cost belonging to a plan; refundable deposits live here too.          |
| `funding_sources` | A funding source belonging to a plan; status drives the gap.           |
| `payment_events`  | A bill the student expects to pay: due date, amount, currency, status, |
|                   | optional recurrence and optional plan link (Phase 2).                   |
| `savings_goals`   | A target amount + target date the student is saving toward (Phase 2).  |

All tables share:

- `id` — UUID primary key, generated by the application.
- `created_at` / `updated_at` — timestamptz, auto-stamped.
- Foreign keys to `users.id` use `ON DELETE CASCADE`, so removing a
  user removes every row they own. `cost_items.source_id` and the
  `*_plan_id` columns on Phase 2 tables use `ON DELETE SET NULL` so
  deleting a source/plan does not orphan the rows that cited it.

## Migrations

Alembic is the source of truth. From `services/api/`:

```bash
source .venv/bin/activate
alembic upgrade head         # apply all pending migrations
alembic downgrade -1         # roll back one revision
alembic revision -m "msg"    # create a new revision (autogenerate optional)
```

Migration history:

- `0001_init.py` — `users` + `sessions`.
- `0002_phase1_readiness.py` — `data_sources`, `exchange_rates`,
  `study_plans`, `cost_items`, `funding_sources`.
- `0003_phase2_payments.py` — `payment_events`, `savings_goals`.

## Decimal columns

Money is stored as `NUMERIC(18, 4)` so the database never silently
truncates a value the engine produced. The calculation engine always
returns Decimal values rounded to the destination currency's natural
precision (e.g. 0 dp for JPY, 2 dp for USD) before they reach the DB.
The extra 2 dp of headroom in the column lets us change rounding
rules later without re-loading data.

## Booleans

PostgreSQL booleans default to `FALSE` (not `0`) on insert. The
Alembic migrations use `server_default=sa.false()` accordingly.

## Ownership

Every query through the repositories layer is scoped by `user_id`.
This is the only safe default; even a tiny ad-hoc query that forgets
the scope leaks another user's data. The API tests in
`app/tests/api/test_ownership.py` (and the `test_other_user_cannot_see_plan`
case in `test_study_plans.py`) prove this end-to-end.
